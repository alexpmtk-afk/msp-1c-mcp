# MSP Bitrix24 → 1C NewBase: изолированный контур заявок v1

Дата: 2026-10-22. Статус: **DESIGN / READ-ONLY ONLY**. Включение, новый webhook, роль записи в 1С, публикация HTTPS, CRM-поля, реальные CRM/OData записи **НЕ выполнены**.

## 1. Задача и инварианты

Пользователь заполняет в Битрикс24 данные нового/имеющегося покупателя и заявку на продукцию. По явному действию «Отправить в 1С» данные попадают в **отдельный** обработчик и после валидации создают покупателя и/или **непроведённый черновик счёта** в исключительно тестовой 1С `D:\DATA\NewBase`.

**Обычное «Сохранить» не создаёт ничего в 1С:** черновик CRM можно менять сколько угодно раз. Первоначальный UI — отдельная стадия CRM-сделки «Передать в 1С» (точные stageId/categoryId определяются реальным read-only аудитом портала); отдельная кнопка возможна впоследствии через согласованное приложение Bitrix24.

Существующие задачи 1С → SQLite → Битрикс24 (включая 30-минутное обнаружение, 5-минутную очередь новых покупателей, 07:45 сверку и выключенный утренний CRM worker) **не менять и не переиспользовать в качестве пишущего агента**. Использовать отдельное пространство задач, логов, credentials, локальную очередь и отдельный Windows Scheduled Task. Никакого изменения рабочей информационной базы 1С.

## 2. Канонический путь и минимально рискованный MVP

1. Сотрудник сохраняет **сделку** в Битрикс24 с клиентом, товарами, количеством, ценой; переводит на согласованную стадию «Передать в 1С».
2. Новый автономный **SRV**-агент `MspBitrixToOnecTestWorker`, работающий под выделенным непривилегированным системным контекстом, выполняет **исходящие** REST-запросы в Битрикс24. Это соответствует уже проверенному сетевому маршруту SRV → Bitrix24 и не требует входящего соединения к устаревшему Windows Server.
3. В **первом MVP** агент по таймеру обнаруживает только сделки целевой стадии через `crm.item.list(entityTypeId=2)`; получая ID, перечитывает объект через `crm.item.get(entityTypeId=2)`, связанные реквизиты и строки товаров через `crm.item.productrow.list(filter: {"=ownerType":"D","=ownerId":ID})`. Складывает нормализованный снимок в **новую** локальную SQLite-очередь на SRV.
4. Перед исполнением проверяет неизменность утверждённого снимка (стадия, IDs, состав строк, версия/хеш). Если карточка изменена после отправки — переводит в REVIEW / требуется повторная отправка. Данные из события/предыдущей карточки не считать актуальными.
5. По утверждённому контракту: наличие действующей связи CRM company/contact ID ↔ 1C Ref_Key; у нового покупателя — контролируемый поиск возможного дубля по ИНН и подтверждённым реквизитам, без автоматического слияния по одному названию.
6. Только после отдельной активации записи и выдачи **новой** строго ограниченной учётной записи 1С через loopback OData создавать `Catalog_Контрагенты` (если действительно нет существующего), затем черновик выбранного `Document_...`. **Название Document EntitySet не предполагать**, определить по реальному `$metadata` NewBase и бизнес-логике УНФ. Без проведения, печати, отправки клиенту, движения денег или складских операций.
7. OData GET по возвращённому Ref_Key подтверждает факт создания, номера/ссылки. Связь и результат фиксируются в изолированной транзакционной очереди, статус/номер возвращаются в Битрикс24 через его REST (после отдельного утверждения поля/владения). Действия обратного CRM update никогда не создают новый 1С запрос.
8. Hermes на VPS получает **только статус и обезличенные метрики** по разрешённому каналу. У Hermes нет права непосредственной записи в 1С и нет необходимости хранить CRM PII на VPS.

Преимущества первого MVP: **нет новой публичной точки приёма**, не открываем 1С наружу, данные остаются на SRV и в уже связанных системах, не затрагиваем работающую инфраструктуру. Минус: задержка обработки равна интервалу опроса; интервал согласовать после измерения нагрузки. Начать с малого лимита, например **1 команда за проход**.

## 3. Возможное событие для ускорения после MVP

При реальной необходимости мгновенного реагирования: исходящий webhook Битрикс24 `ONCRMDEALUPDATE` на отдельный согласованный HTTPS endpoint VPS. Для подлинности проверять **auth.application_token, member_id и фиксированный домен**; событие содержит только CRM ID, не полный доверенный payload. После долговременной записи минимального event ID/CRM ID — быстрый HTTP 2xx. SRV забирает задание только **исходящим** запросом, затем заново читает данные CRM. Реестр событий должен быть дедуплицирован.

**Webhook/публичный endpoint ещё не созданы**. Существующий прототип `bitrix_relay/` — read-only поиск и **NOT DEPLOYED**, не считать готовым приёмником событий. Исходящий webhook и входящий webhook Битрикс24 — разные механизмы. Не передавать секреты через URL, GitHub, Telegram, issue comments. Рекомендации производителя: https://apidocs.bitrix24.com/local-integrations/local-webhooks.html ; https://apidocs.bitrix24.com/settings/performance/queue.html .

## 4. Разделение сущностей и контрактов

| Операция | Триггер | Обязательные входные признаки | Итог и запреты |
| --- | --- | --- | --- |
| `CUSTOMER_ENSURE` | Явная передача, клиент указан | CRM тип + ID, тип физ/юр, проверенные реквизиты, сопоставление `onec_guid` | Найти существующего или создать **в NewBase** только после проверки дублей; не перезаписывать клиента вслепую |
| `INVOICE_DRAFT_CREATE` | Явная передача сделки со строками | Deal ID, клиент, товары, количество, цена, валюта, налоги/скидки если используются, определённые GUID номенклатуры | Один **непроведённый** счёт в тестовой 1С; номер/Ref_Key с обратным чтением; не проводить |
| `ORDER_DRAFT_CREATE` | Будущая отдельная операция | Отдельный контракт заказа покупателя и выбранная 1C сущность | **Не реализовывать** под видом счёта |

Поля и формы в Битрикс24 выяснить через `crm.item.fields`, `crm.category.list`, `crm.status.list`, `crm.item.get`, `crm.item.productrow.fields/list`, `crm.requisite.list` **только для согласованных тестовых объектов**. Для непомеченных CRM-карточек новая интеграция вообще ничего не делает.

Проверить в 1C NewBase реальные EntitySets `Catalog_Контрагенты`, `Catalog_Номенклатура`, необходимые справочники и документ счёта; точные поля/табличную часть GET $metadata. Стандартный OData POST технически может создавать объекты/документы, но **это не доказывает ни права текущего пользователя, ни что код 1С корректно заполнит нужные реквизиты**.

Источником истины для связи клиента служат стабильные CRM ID + entity type и 1С Ref_Key; существующую SRV таблицу соответствий **использовать только в режиме чтения**, копия/передача в новую командную очередь лишь по проверенному контракту. Не делать дублирующих компаний/контактов при ежедневном чтении 1C → Bitrix24. Поля по направлениям владения (1C-owned vs CRM-owned) определить отдельно.

## 5. Доставка команд и безопасность

Новый журнал (отдельная SQLite, не `C:\ProgramData\MspCustomerStore\data\customers.db`):

- `commands`: `request_id` UNIQUE, `crm_type`, `crm_id`, `crm_version`, `operation`, `payload_hash`, `status`, `created_at`, `updated_at`.
- `onec_results`: `request_id` UNIQUE, `onec_ref_key`, `onec_number`, `readback_verified`, `result_at`.
- `audit`: обезличенная запись переходов состояния, без ФИО/ИНН/токенов в отчётах.

Состояния: `DISCOVERED → VALIDATED → APPROVED_TEST → WRITE_INTENT → READBACK_VERIFIED → COMPLETE`; ветки `HELD_DUPLICATE`, `HELD_MISSING_FIELDS`, `HELD_UNMAPPED_PRODUCT`, `HELD_STALE_SOURCE`, `UNCERTAIN_WRITE`, `FAILED_SAFE`. Нельзя переходить в `COMPLETE` после одного HTTP 200 без фактического обратного чтения.

Защита от повторного создания: уникальный `(crm_type,crm_id,operation,approved_version)`, неизменяемый idempotency key, локальная фиксация `WRITE_INTENT` **до** OData POST. При timeout/неоднозначном ответе — проверить результат поиска/прочтения по надёжной связи и при недоказанности остановиться в `UNCERTAIN_WRITE`, **не повторять POST автоматически**. Требуется согласовать способ сохранения внешнего CRM request ID в объекте 1C, если стандартного реквизита нет — нужна безопасная отдельная связующая таблица и операторский разбор сомнительных попыток.

Операции проверки должны использовать существующую read-only учётную запись. Для записи создать отдельную **TEST-only** учётную запись по принципу минимально необходимых прав; действующую `MCP_OData_ReadOnly` не расширять. Секрет в DPAPI/защищённом хранилище на SRV, не в публичном Git. Нет `DELETE`, `PATCH` на произвольные сущности, проведения `/Post`, свободной передачи OData URL, вызова произвольного shell. Этапы чтения/записи и полномочия разграничить.

Внешняя запись требует отдельных согласий после проверки: реальной модели документов/реквизитов; роли 1C; synthetic end-to-end; лимитов; rollback; настройки CRM. Продакшн-1С не затрагивается.

## 6. Проверяемая последовательность работ

- **P0 (сейчас, безопасно):** аудит существующего SRV Bitrix REST доступа и доступных методов CRM **без правок**; OData `$metadata` NewBase для `Catalog_Контрагенты`, документа счёта, табличных частей; статус пользовательских настроек Битрикс24, существующих связей, наличие поля стадии/продуктов. Никаких новых сущностей.
- **P1:** зафиксировать `categoryId`, `stageId`, схему тестовой CRM формы и карту поля→OData. Дать пользователю короткий сценарий интерфейса; не менять текущие сделки без согласования.
- **P2:** автономная SQLite inbox, чистые валидаторы и тесты на синтетике — NEW_BUYER, EXISTING_BUYER, INVOICE, DOUBLE_CLICK, CRM_EDIT_DURING_PROCESSING, AMBIGUOUS_POST, ODATA_OFFLINE, MISSING_PRODUCT. Реальных подключений нет.
- **P3:** только read-only получение **одного тестового** CRM ID и формирование `PREVIEW` команды; никаких OData POST.
- **P4:** только после отдельного согласия — тестовая OData роль записи и единичная synthetic create контрагента в NewBase с обратным чтением; проверить откат/удаление тестового мусора только вручную.
- **P5:** отдельно approve и один непроведённый счёт на синтетического контрагента с разрешённой номенклатурой в NewBase; сверить номер, суммы, строки, непроведение.
- **P6:** проверка статуса в Bitrix24, защита от петель, ошибок, повторов, резервные копии, ограниченный автоматический запуск **только на тестовых карточках**.
- **P7:** отдельное бизнес- и техническое решение о возможном продакшн-доступе, не входит в этот этап.

## 7. Вопросы, которые закрывает read-only аудит

1. Как в Bitrix24 сейчас создаются заявки: сделка, смарт-процесс или отдельная форма? Существующие поля и воронки нельзя угадывать.
2. Какой реальный `Document_...` в 1C UNF 3.0.13.314 соответствует нужному **счёту на оплату** и какие обязательные реквизиты?
3. Где хранится поставка номенклатуры из Битрикс24 в GUID 1C и есть ли качественная карта товаров?
4. Какие поля сохраняются за Bitrix24, какие — за 1C, чтобы две независимые системы не перезаписывали друг друга?
5. Какие обязательные реквизиты заказчика и документа нужны бизнесу: подразделение, организация, договор, НДС, ставка, валюта, склад и прочее?
6. Нужен ли приоритет **реального времени**; если нет, первый MVP работает без входящего webhook через безопасное исходящее чтение.
7. Проверена ли фактическая работа старого Windows с OData POST в **тестовой** базе? Пока ответ — **нет**.
