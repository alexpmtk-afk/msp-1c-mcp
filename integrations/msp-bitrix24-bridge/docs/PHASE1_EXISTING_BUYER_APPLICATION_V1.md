# Bitrix24 → TEST NewBase: этап 1 — заявка существующего покупателя

**Решение владельца от 22.10.2026:** первым этапом поддержать **только уже существующее юридическое или физическое лицо в 1С**. Целевой тип документа однозначно утверждён владельцем: **«Заказ покупателя»**, не «Счёт на оплату». Создание нового контрагента, изменение реквизитов контрагента, проведение документов и любая запись в рабочую 1С исключены из этого этапа.

**Статус:** SPECIFICATION / NO DEPLOY / NO ODATA WRITE. Этот документ заменяет более широкий исходный scope раннего черновика `BITRIX_TO_ONEC_TEST_INBOX_V1.md` исключительно для реализации этапа 1.

## 1. Пользовательский сценарий

1. Сотрудник открывает сделку/заявку в Битрикс24, выбирает **уже имеющегося** покупателя (CRM company для юрлица либо CRM contact для физлица; нет автоматического переноса данных из одной категории в другую).
2. Добавляет одну или несколько строк товаров, количество и согласованные цены, при необходимости заполняет проверенные поля НДС/скидки/валюты/организации.
3. Явно вызывает действие «Отправить в 1С» или, после отдельной согласованной настройки, переводит сделку в особую стадию. **Обычное «Сохранить» не означает отправку**, чтобы частичные карточки и повторные сохранения не создавали документы.
4. Новый изолированный агент на SRV читает исходящими вызовами REST актуальную версию сделки и связанных полей. Выделяет клиента, строки товаров и метаданные заявки. Фиксирует нормализованный снимок в отдельной локальной командной SQLite; никаких сведений о клиентах в GitHub/VPS.
5. Находит ранее подтверждённую пару `(entityTypeId, CRM entity id) -> Ref_Key 1C` в существующем машинном справочнике соответствий SRV, **только через read-only доступ**. Дополнительно GET в TEST `Catalog_Контрагенты` по Ref_Key: контрагент существует, не помечен удалённым/недействительным, соответствует типу физ/юр, допускает оформление документа. Не искать «подходящего» покупателя только по ФИО, названию или ИНН.
6. Каждую строку сопоставляет с подтверждённым `Catalog_Номенклатура` и соответствующим GUID. Не угадывать товары по сходству названий или несовпадающему SKU. Не позволять сумму 0/отрицательное количество и не превращать неизвестную ставку налога в 0.
7. Проверяет документную модель `$metadata` OData тестовой 1С, обязательные реквизиты, наличие подтверждённого типа документа и корректность сумм. **«Заявка» в Битрикс24 преобразуется только в документ 1С «Заказ покупателя» (решение владельца подтверждено). Проверить фактические OData EntitySet, имя объекта, состав табличных частей и обязательные реквизиты в `$metadata` тестовой UNF; не придумывать `Document_...` до реальной проверки.**
8. Только после отдельного допуска TEST OData write: записывает один **непроведённый** черновик указанного документа. Перед POST сохраняет `WRITE_INTENT` с неизменяемым request ID; после ответа перечитывает документ по Ref_Key и проверяет клиента, строки, суммы, статус непроведения и связку с CRM ID.
9. После подтверждённого readback сохраняет результат и обновляет статус в соответствующей CRM-заявке (после отдельного одобрения полей Bitrix24). Не связывать служебную запись статуса с новым триггером передачи.
10. Неясный результат POST, сетевой timeout, двусмысленный mapping, неподтверждённая номенклатура, изменение сделки после отправки или неполные поля переводят операцию в `HELD_...` / `UNCERTAIN_WRITE`, **без автоматического повторного POST** и без создания дубля.

## 2. Входной контракт (утвердить по реальной CRM-схеме)

| Бизнес-данные | Источник | Проверка |
| --- | --- | --- |
| Идентификатор заявки / сделки, CRM version, явный статус отправки | Bitrix24 | Строго один разрешённый класс/стадия, свежий readback |
| CRM buyer `entityTypeId` + ID | Bitrix24 company/contact | Пара с 1C Ref_Key однозначна, не дублируется |
| Тип покупателя: юридическое/физическое лицо | mapping + 1C GET | Оба типа поддержаны; `REVIEW` и несоответствия блокируют |
| Существующий GUID контрагента | SRV readonly mapping + NewBase OData | Только существующий и допустимый покупатель |
| Товары, количество, цена | CRM строки | Все товары однозначно сопоставлены с GUID номенклатуры 1C |
| НДС, валюта, скидки, организация, договор и другие реквизиты | CRM + выбранный документ 1C | Обязательность определить из реальных метаданных/проверок UNF |
| Тип целевого документа | Решение владельца | **CONFIRMED: документ «Заказ покупателя»**; техническое OData-имя и обязательные реквизиты **PENDING metadata verification** |
| Результат | OData readback | `Document Ref_Key`, номер, связь со сделкой, не проведён |

**Отказные сценарии:** buyer отсутствует в mapping; устаревшая/неактивная 1C запись; неверная категория CRM; покупатель уже есть, но CRM связь не подтверждена; неопределённая номенклатура; конфликт поля/налога; повторное нажатие; неизвестный итог POST; CRM документ изменён после первоначального чтения.

## 3. Техническая изоляция

- Существующий контур **1С → SQLite → Bitrix24**, включая дневные задания и 07:45, **НЕ менять**.
- Новый SRV runner — отдельный Scheduled Task и отдельная SQLite очереди; исходящие запросы SRV → Bitrix24, локальные запросы на `127.0.0.1:8085` → `D:\DATA\NewBase`. Новый публичный callback и VPS-передача клиентских реквизитов **не нужны для MVP**.
- Существующая учётная запись `MCP_OData_ReadOnly` остаётся неизменной. Для будущего OData POST — отдельная TEST-only учётная запись только с разрешениями на выбранный документ, защищённые DPAPI credentials и строгие ACL; не выдавать произвольные write CRUD инструменты Hermes.
- Hermes может получать обезличенные статусы, но не исполнять произвольные OData POST и не иметь секретов/PII на VPS.
- `(CRM deal ID, action type, approved revision)` UNIQUE; явный request ID/intent до OData POST; подтверждение readback обязательно. Не допускать две операции в одном и том же 1C документе и параллельных дублей.
- Пилот ограничить одной специально выбранной **существующей** тестовой записью юридического лица либо физического лица с рабочим mapping и несколькими тестовыми строками номенклатуры. После успешного цикла проверить второй тип покупателя, не меняя контрагента.
- Нет `POST Catalog_Контрагенты`, никаких `PUT/PATCH` контрагента, проведения/печатной отправки документов, изменений остатков/цен, продакшн-1С.

## 4. Порядок реализации

**P0 read-only:** на реальном SRV/Bitrix24 установить актуальный CRM тип заявок, тип связи с buyer, список разрешённых стадий, наличие продуктовых строк; из TEST `$metadata` определить перечень доступных документов `Document_...` и обязательные поля, получить schema-only/GET пробы; проверить наличие CRM→1C linkage для company и contact и точность source GUID. Без полного повторного чтения 6435 контрагентов.

**P1 source contract:** тип документа **«Заказ покупателя» утверждён**. Владелец отдельно выбирает штатный пользовательский триггер (кнопка или стадия); по проверенному EntitySet заказа и табличной части составить карту реквизитов. Не реализовывать создание «Счёта на оплату» в этапе 1.

**P2 offline:** изолированный inbox, validation, idempotency, реестры статуса/полей и synthetic tests. Без SRV network/CRM/1C writes.

**P3 real read-only preview:** прочитать 1 специально выбранную CRM заявку с уже существующим клиентом и создать только PREVIEW готовой к передаче операции; вывести агрегированный результат без личных данных.

**P4 TEST-write, отдельное согласие:** установить учётную запись минимальных прав, после bounded snapshot и резервной копии схемы/локальных данных создать только 1 непроведённый документ в TEST `NewBase`. Readback и доказательство отсутствия дубля. Для юридического и физического лица — самостоятельная приёмка.

**P5 CRM result/status + opt-in automation:** после разрешения владельца добавление статуса/ссылки в Битрикс24 и проверка повторных нажатий/ошибок. Работающая дневная система 1С→CRM не затрагивается.

## 5. Критерий готовности этапа 1

Для одного **уже существующего** юридического лица и одного **уже существующего** физического лица:
- сопоставление CRM ID ↔ 1C Ref_Key подтверждено;
- 1C клиент не создавался/не изменялся;
- все строки товаров сопоставлены и проверены;
- создаётся ровно один **непроведённый «Заказ покупателя»** в NewBase;
- клиент, товарные строки, суммы и отсутствие проведения подтверждены OData GET;
- CRM получила подтверждённый номер и статус;
- повторная передача не создаёт дублей;
- рабочая 1C, действующий контур 1C→CRM, Gateway и другие службы не изменены.

**По состоянию на 22.10.2026:** это критерии будущей приёмки, не выполненный результат. Для P0/P1 достаточно read-only проверки, никаких новых сущностей не создавать.
